How should scale weigh-in records be stored?

A weigh-in captures: customer, product, weight, photos, order number. It has NO price yet — pricing happens at reception. Which data model fits best?

A

New lightweight ScaleOrder model (recommended)

A dedicated ScaleOrder table: orderNumber, customerId, productId, weight, photoR2Keys, status (pending → processed → voided), operatorId, createdAt.

Pros

  • Purpose-built — no nullable price/payment fields
  • Clean status lifecycle: pending → processed → voided
  • Order number format SCL-20260523-0001 is easy to generate
  • Reception links it to a Purchase when paying
  • Reports are simple: all ScaleOrders, filterable by status/date/operator
  • Doesn't pollute the Purchase table with unpaid weigh-ins

Cons

  • New Prisma migration required
B

Reuse the existing Purchase model

Create a Purchase with status: pending and totalAmount: 0 at the scale. Reception completes it by adding price and marking it paid.

Pros

  • No new DB model needed
  • Existing purchase reports include scale records automatically

Cons

  • Purchase requires paymentMethod, unitPrice, lineTotal — all would be null/zero
  • Scale-station orders visible in the main purchase list — confusing
  • Audit trails mix scale records with real purchases
  • Order numbers would follow the existing purchase ref format (not SCL-*)

💡 My recommendation: Option A — a dedicated ScaleOrder model keeps weigh-ins clean, separate, and purpose-built. It avoids polluting the Purchase table and makes fraud detection straightforward (compare ScaleOrders vs Purchases).
