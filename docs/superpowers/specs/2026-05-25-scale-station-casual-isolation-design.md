# Scale Station — Casual Customer Isolation

**Date:** 2026-05-25  
**Status:** Approved

---

## Problem

When a Scale Station operator enters a walk-in (casual) customer, the wizard calls `POST /api/customers/quick-create`, which creates a real `Customer` row with `customerType: casual`. That row immediately appears in the Casual Details module of the main admin system. Scale-station walk-ins should never populate the main customer table.

## Goal

Walk-in customer details entered on the Scale Station must be stored **only on the `ScaleOrder` record**. No `Customer` row is created. The Casual Details module, the Accounts module, and every other part of the main system remain completely untouched.

Account customers (existing registered customers looked up via search) continue to work exactly as before.

---

## Approach — Inline Casual Fields on ScaleOrder

Add three nullable columns to `ScaleOrder`:

| Column | Type | Purpose |
|---|---|---|
| `casualFirstName` | `String?` | Walk-in first name |
| `casualLastName` | `String?` | Walk-in last name |
| `casualPhone` | `String?` | Walk-in phone |

Make `customerId` nullable (`String?` instead of `String`).

**Invariant:** Every `ScaleOrder` satisfies exactly one of:
- `customerId IS NOT NULL` — account customer order (FK to Customer table)
- `customerId IS NULL AND casualFirstName IS NOT NULL` — walk-in order (inline fields)

All existing orders have `customerId` set; they are untouched by this migration.

## What Changes

### 1. `prisma/schema.prisma`

```prisma
model ScaleOrder {
  id              String           @id @default(uuid())
  orderNumber     String           @unique
  customerId      String?          // nullable — null for walk-in orders
  casualFirstName String?
  casualLastName  String?
  casualPhone     String?
  productId       String
  weight          Decimal          @db.Decimal(18, 3)
  photoR2Keys     String[]
  slipR2Key       String?
  status          ScaleOrderStatus @default(pending)
  operatorId      String
  notes           String?
  voidedAt        DateTime?
  voidedById      String?
  voidReason      String?
  createdAt       DateTime         @default(now())
  updatedAt       DateTime         @updatedAt

  customer   Customer?     @relation(fields: [customerId], references: [id])
  product    ScaleProduct  @relation(fields: [productId], references: [id])
  operator   User          @relation("ScaleOrderOperator", fields: [operatorId], references: [id])
  voidedBy   User?         @relation("ScaleOrderVoidedBy", fields: [voidedById], references: [id])

  @@index([customerId])
  @@index([productId])
  @@index([operatorId])
  @@index([status])
  @@index([createdAt])
}
```

Prisma migration SQL (generated by `prisma migrate dev`):
```sql
ALTER TABLE "ScaleOrder" ALTER COLUMN "customerId" DROP NOT NULL;
ALTER TABLE "ScaleOrder" ADD COLUMN "casualFirstName" TEXT;
ALTER TABLE "ScaleOrder" ADD COLUMN "casualLastName" TEXT;
ALTER TABLE "ScaleOrder" ADD COLUMN "casualPhone"    TEXT;
```

All existing rows keep their `customerId` values; migration is fully backward compatible.

### 2. `src/app/scale/components/Step1Customer.tsx`

**Casual mode — remove the `quick-create` API call entirely.**

The `handleCasualSubmit` function currently:
1. Calls `POST /api/customers/quick-create`
2. Returns the new customer's `id`

New behaviour:
1. Simply calls `onSelect({ id: null, firstName, lastName, phone, isNew: true })` directly from the form submit — no API call, no Customer row.

The `SelectedCustomer` interface gains `id: string | null`:

```typescript
export interface SelectedCustomer {
  id:        string | null   // null = walk-in (no Customer row)
  firstName: string
  lastName:  string
  phone:     string
  isNew?:    boolean
}
```

Account mode is unchanged — it still sets `id` to the looked-up customer's UUID.

### 3. `src/lib/schemas/scaleSchemas.ts` (or wherever the order create schema lives)

Update the order creation Zod schema to accept either a `customerId` **or** inline casual fields, with a refinement that ensures at least one is present:

```typescript
export const CreateScaleOrderSchema = z.object({
  customerId:      z.string().uuid().optional(),
  casualFirstName: z.string().min(1).optional(),
  casualLastName:  z.string().min(1).optional(),
  casualPhone:     z.string().min(7).optional(),
  productId:       z.string().uuid(),
  weight:          z.string().regex(/^\d+(\.\d{1,3})?$/),
  photoR2Keys:     z.array(z.string()).min(0),
}).refine(
  d => d.customerId || (d.casualFirstName && d.casualLastName && d.casualPhone),
  { message: 'Either customerId or casual customer details (firstName, lastName, phone) are required' },
)
```

### 5. `src/lib/services/scaleService.ts`

Add a helper to resolve display name and phone from either source:

```typescript
type OrderWithCustomer = {
  customer:       { firstName: string; lastName: string; phone: string } | null
  casualFirstName: string | null
  casualLastName:  string | null
  casualPhone:     string | null
}

export function resolveCustomerName(o: OrderWithCustomer): string {
  if (o.customer) return `${o.customer.firstName} ${o.customer.lastName}`
  return `${o.casualFirstName ?? ''} ${o.casualLastName ?? ''}`.trim() || 'Walk-in'
}

export function resolveCustomerPhone(o: OrderWithCustomer): string {
  return o.customer?.phone ?? o.casualPhone ?? ''
}
```

Update `include` in `listScaleOrders` and `getScaleOrderById` so the customer relation is included as before (Prisma returns `null` when `customerId` is null — no code change needed in the include itself; the helper handles the null case).

### 8. `src/app/app/(modules)/scale/...` (frontend orders list/detail)

Any frontend component that accesses `order.customer.firstName` or `order.customer.phone` directly must be updated to handle `order.customer` being `null`. The API response should include the resolved `customerName` and `customerPhone` fields (computed server-side in the route handler before returning JSON), so no raw null reaches the frontend.

**Pattern:** In the list/detail API responses, add computed fields:
```typescript
return {
  ...order,
  customerName:  resolveCustomerName(order),
  customerPhone: resolveCustomerPhone(order),
  customerType:  order.customer?.customerType ?? 'casual',
}
```

## What Does NOT Change

| Area | Status |
|---|---|
| Casual Details module (`/app/casual`) | Untouched — it queries Customer table, which scale walk-ins no longer touch |
| Account customer lookup in Scale Station | Untouched — still reads from Customer table |
| Purchases, Sales, Payments modules | Untouched |
| Existing Scale orders with `customerId` set | Untouched — Customer FK still valid |
| `POST /api/customers/quick-create` endpoint | Remains in the codebase but is no longer called by Scale Station |
| Scale admin pages (categories, products) | Untouched |

---

## Migration Safety

- The Prisma migration is additive: three new nullable columns + one NOT NULL → NULL change on `customerId`.
- All existing `ScaleOrder` rows have a valid `customerId`; nothing breaks on deploy.
- Rollback: the three new columns can be dropped without affecting any other table. Making `customerId` NOT NULL again would only fail if walk-in orders already exist in production (safe to delay rollback until confirmed).
